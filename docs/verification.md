# Проверки и измерение памяти

## Основные команды

```sh
make deps
make check
make verify
make browser
make linux
```

`make check` собирает интерфейс, проверяет TypeScript, запускает Go-тесты с race detector и `go vet`. Для `-race` нужен C-компилятор: Xcode Command Line Tools на macOS или системный C toolchain на Linux. Runtime-бинарник собирается отдельно с `CGO_ENABLED=0`.

`make verify` собирает обычный серверный бинарник и запускает независимые Node.js/Yjs-клиенты через настоящие WebSocket. Межвкладочный обмен отключён. Harness проверяет:

- конкурентные вставки/удаления и изоляцию комнат;
- Unicode и объединение правок после разрыва соединения;
- восстановление текста свежими клиентами из SQLite после SIGTERM и запуска нового серверного процесса;
- сохранение режима Text и доступность короткой ссылки после перезапуска;
- 5 комнат, созданных через API с короткими кодами, по 4 участника и по 100 КиБ исходного текста в каждой;
- 60 секунд распределённых по тексту вставок и удалений с шагом 200 мс у каждого клиента;
- принудительный обрыв пяти соединений и автоматическое переподключение во время нагрузки;
- сходимость всех клиентов и два дополнительных цикла подключения/выхода с проверкой выгрузки комнат и восстановления текста.

Все запущенные проверкой процессы завершаются. Для собственного времени нагрузки:

```sh
make build
npm run test:integration -- --duration=120
```

Машинный результат записывается в `artifacts/latest-report.json`; отдельный запуск и его тестовая база — в `artifacts/verify-*/`. Эти данные не нужны для сборки приложения. Удаляйте их, когда они больше не нужны: повторные прогоны оставляют отдельные базы и отчёты.

## Как читать память

Harness измеряет RSS только отдельно запущенного Go-сервера. Браузер, Node.js-клиенты и компилятор не входят в цифру. На Linux используется `/proc/PID/status`, на macOS — `ps -o rss`. В отчёте также есть Go heap, Go Sys, число goroutine, загруженных комнат, обработчиков WebSocket, PID, ОС, архитектура и версии.

`resident_rooms` считается через hooks загрузки/выгрузки документов. `websocket_handlers` — количество выполняющихся обработчиков: при установке/отклонении подключения возможны краткие переходные значения; в установившемся режиме оно соответствует соединениям.

RSS не обязан немедленно уменьшиться после выхода участников: аллокатор и runtime могут удерживать освобождённые страницы. Проверяйте вместе число комнат, heap и несколько повторений нагрузки. Минутный прогон не доказывает отсутствие утечек на сутках работы.

Чтобы решить, хватает ли VPS с VPN, повторите тот же сценарий на Linux целевой архитектуры, сопоставьте память приложения с `free -h` и `systemctl show kosha -p MemoryCurrent -p MemoryPeak`, проверьте задержку редактирования при обычной нагрузке VPN. Для тестов можно собирать проект на отдельной машине и запускать готовый серверный бинарник через `KOSHA_BINARY`; автоматический harness всегда запускает сервер локально на машине, где запущен harness.

## Браузерная проверка

На macOS по умолчанию используется установленный Google Chrome. На Linux установите тестовый Chromium: `npx playwright install chromium`; системные зависимости при необходимости — по инструкции Playwright. Для другого совместимого Chromium задайте `CHROME_PATH`.

`make browser` запускает два независимых браузерных контекста, проверяет шестисимвольные пути, создание/повторный вход/обновление комнаты, совместимость прежних fragment-ссылок, Text без подсветки и скачивание .txt. Также проверяются общий текст, подсветка Python/SQL, undo/redo только собственных правок с сохранением чужого текста, общее переключение типа, ошибки JavaScript, отсутствие внешних ресурсов и ширина мобильного экрана. Снимки: `artifacts/browser-desktop.png` и `artifacts/browser-mobile.png`.

HTTPS, конфигурация systemd/Caddy, корпоративные сети и фактический бюджет VPS проверяются отдельно при размещении. Кросс-компиляция Linux подтверждает сборку, но не заменяет запуск на Linux.
