# Сборка и размещение

## Требования к машине сборки

- Go 1.26 или новее, Node.js 22.12 или новее, npm, Make.
- Доступ к Go module proxy и npm registry для первой загрузки зависимостей.
- Linux, macOS; сборка Linux-бинарника возможна с macOS. Браузер нужен только для браузерной проверки.

Из корня проекта:

```sh
make deps
make build
./bin/kosha
```

Команда `make build` проверяет TypeScript, собирает интерфейс и встраивает его в `bin/kosha`. Сначала требуется сборка интерфейса: прямой `go build` в свежем клоне без неё не найдёт встраиваемые файлы. Зависимости закреплены в `go.mod`, `go.sum` и `package-lock.json`; `make deps` использует `npm ci --ignore-scripts`.

Откройте [редактор](http://127.0.0.1:8080). Остановка — Ctrl+C; процесс завершает соединения и дожидается записи накопленных изменений. Кэши сборки остаются в `.cache/` проекта, бинарники — в `bin/`, база по умолчанию — `data/kosha.db`.

## Перенос на Linux VPS

Собирайте на рабочей машине, чтобы не занимать память VPS компилятором:

```sh
make linux
# Для ARM64-сервера:
make linux TARGET_ARCH=arm64
```

Получатся `bin/kosha-linux-amd64` или `bin/kosha-linux-arm64`. Бинарник не использует CGO и содержит интерфейс. На сервере нужны только сам файл, каталог данных и HTTPS-прокси для удалённого доступа.

Пример для Debian/Ubuntu с systemd; замените `your-server` и выберите подходящую архитектуру:

```sh
scp bin/kosha-linux-amd64 your-server:/tmp/kosha
scp deploy/kosha.service your-server:/tmp/kosha.service
ssh your-server
sudo useradd --system --home /var/lib/kosha --shell /usr/sbin/nologin kosha
sudo install -d -m 755 /opt/kosha
sudo install -m 755 /tmp/kosha /opt/kosha/kosha
sudo install -m 644 /tmp/kosha.service /etc/systemd/system/kosha.service
sudo systemctl daemon-reload
sudo systemctl enable --now kosha
curl --fail http://127.0.0.1:8080/healthz
sudo journalctl -u kosha -n 50 --no-pager
```

Если пользователь `kosha` уже существует, повторно создавать его не нужно. systemd создаёт каталог состояния `/var/lib/kosha`; база находится в `/var/lib/kosha/kosha.db`. Сервис использует loopback, мягкий ориентир Go-памяти 192 МиБ и жёсткий предел cgroup 256 МиБ. Это начальные настройки: сопоставьте их с нагрузочным прогоном на своём VPS. Память cgroup включает больше, чем один RSS процесса; превышение жёсткого предела может завершить процесс.

Для личной проверки без публичного HTTPS можно открыть SSH-туннель с рабочей машины:

```sh
ssh -L 8080:127.0.0.1:8080 your-server
```

После этого используйте [локальный адрес туннеля](http://127.0.0.1:8080). Для ссылки, работающей у других участников, нужен общий доступный домен.

## HTTPS и доступ участников

Перед размещением проверьте свободную память под обычной нагрузкой VPN и владельца портов:

```sh
free -h
sudo ss -ltnp
```

Если VPN или существующий прокси занимает TCP 443, сначала настройте совместное использование через имеющийся прокси; второй сервис не сможет слушать тот же адрес и порт. Для Caddy с автоматическим HTTPS обычно нужны домен с DNS-записью на сервер и входящие TCP 80/443.

Установите Caddy по [официальной инструкции](https://caddyserver.com/docs/install), затем используйте [пример конфигурации](../deploy/Caddyfile.example). Замените домен и `REPLACE_WITH_CADDY_PASSWORD_HASH`. Хэш получите интерактивно командой `caddy hash-password`; открытый пароль не записывайте в конфигурацию или Git. Добавьте блок в существующий Caddyfile, сохранив остальные сайты.

```sh
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl reload caddy
```

Пример закрывает весь прототип общим паролем и скрывает диагностику. Передайте пароль участникам отдельно от ссылки. Это временная схема для технического прототипа: отдельного права «создавать комнаты только владельцу» пока нет. Публичное анонимное размещение без контроля доступа не предусмотрено.

Caddy [поддерживает WebSocket](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy) при обычном `reverse_proxy`. Если используете существующий nginx, настройте [передачу Upgrade/Connection и таймауты](https://nginx.org/en/docs/http/websocket.html). Проксируйте все пути приложения, включая страницы `/Q1W2E3`, `/api/rooms`, `/assets/` и `/yjs/`: маршруты коротких ссылок обрабатывает сам Go-сервер. Сохраняйте исходный Host: сервер проверяет Origin на соответствие Host. Не открывайте порт приложения 8080 наружу.

Проверьте HTTPS-ссылку минимум из двух сетей участников. Собственный домен не гарантирует доступность IP или WebSocket в каждой корпоративной сети.

## Обновление и резервные копии

Заменяйте бинарник после сборки, затем выполняйте `sudo systemctl restart kosha`. Попросите участников обновить вкладки, чтобы загрузить новый интерфейс. Не удаляйте каталог состояния. Сначала проверяйте восстановление на копии базы при изменении версий ygo/Yjs.

Для простой согласованной резервной копии остановите сервис, скопируйте весь каталог состояния и запустите его снова:

```sh
sudo systemctl stop kosha
sudo tar -C /var/lib -czf /root/kosha-backup.tar.gz kosha
sudo systemctl start kosha
```

Для копирования работающего сервиса используйте SQLite backup API/команду `.backup`. Не копируйте только файл `.db` у работающей WAL-базы: свежие данные могут находиться в `-wal`.

Файлы unit/Caddy — примеры размещения. Их работа на конкретном Linux VPS, HTTPS и сосуществование с VPN должны быть проверены на этом сервере.
